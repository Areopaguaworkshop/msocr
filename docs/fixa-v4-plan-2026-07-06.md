# Fix A v4: Closing the Overfit Gap (71.43% train 6% / val-holdout 60-71%)

Status: builds on `fix-a-v3-syriac-script-finetune.md` (SHIPPED, 71.43%
holdout). v3 correctly diagnosed and fixed underfitting (0.2, more epochs).
What's left is a different problem — severe overfitting — and it needs
different tools than v3's plan had. This doc adds one new mechanism v3
didn't have (a likely explanation for the 87.3%-shared-class-error finding
from 0.1) plus a corrected, much cheaper path for the synthetic-data lever.

## 1. New finding: `--freeze-backbone` doesn't freeze the classifier

This is the headline item — it changes the diagnosis of your own 0.1
confusion-matrix result.

Kraken's own documentation defines `--freeze-backbone` explicitly as
freezing everything **except the last fully-connected/classification
layer**. That means across every run so far (v2's 3.2, v3's 0.2), the
*entire* 42-way classifier — all 37 old rows plus the 5 new rows — has been
trainable the whole time. Nothing about `union` or `--freeze-backbone`
actually protects the 20+ shared Syriac consonant weights once training
starts.

This gives a concrete alternative explanation for 0.1's finding that 87.3%
of errors are on *shared* classes: those rows aren't failing because of
leftover CTC-alignment noise — they're drifting because they keep getting
gradient updates from a 148-line sample whose character frequency
distribution doesn't match whatever the original Sophro training corpus
looked like. Kraken's own docs carry a related warning for fine-tuning in
general: using `union`/`add` risks the network "rapidly unlearning" labels
that aren't adequately represented in the new, smaller dataset — which is
exactly what a "148 lines vs. whatever Sophro originally trained on" mismatch
would produce, and is consistent with deletions (not substitutions)
dominating the error profile: a classifier row whose weights have drifted
toward "predict blank" for an underrepresented class shows up as a deletion.

0.2's 200-epoch fix helped because more training time gave the *new*
classes more chances to be learned before early stopping — but it also gave
the drifting *old* rows 3.3x more chances to drift, which is consistent with
the severe train/val gap that opened up (45%→6% train, but val/holdout only
improved ~6 points). More epochs was the right call for the underfitting
problem, but it's now pulling in two directions at once.

### The fix: freeze the old-class classifier rows explicitly, not just the backbone

This can't be done through `ketos train` CLI flags — there's no per-row
freeze option — so it needs a small Python-API-level change rather than a
new flag combination:

1. Load the model via kraken's Python API (`kraken.lib.vgsl.TorchVGSLModel`)
   after `--resize union` has been applied (or replicate the resize step
   in Python directly).
2. Identify the output layer's weight/bias tensor and the row indices
   corresponding to the 5 new Sogdian classes vs. the ~37 old classes
   (the codec dump from the 0.1/3.1 audit work already has this mapping).
3. Register a backward hook (`tensor.register_hook`) on the classifier
   weight and bias that zeroes the gradient for all rows except the new-class
   rows, before the optimizer step. This makes the old-class rows
   mathematically frozen — no possible drift — while the 5 new-class rows
   train normally.
4. Drive this through kraken's `KrakenTrainer` / Lightning training loop
   (rather than a bespoke training loop) so the rest of the pipeline
   — checkpointing, early stopping, `--augment`, evaluation — is unchanged
   and results stay comparable to v2/v3.
5. Re-run the identical 0.2 recipe (`--resize union --freeze-backbone
   999999 --epochs 200 --lag 25 --lr 1e-4 --augment`) with only this one
   change, and re-triangulate on the same three plates (c2av01/11/12).

**Expected outcome:** if this hypothesis is right, shared-class accuracy on
holdout should move back toward the base Sophro model's original accuracy on
plain Syriac text (i.e., close to the ~99% territory kraken reports for
well-trained Syriac models), the train/val gap should shrink substantially
(train CER won't need to hit 6% anymore, since old rows can't overfit),
and any remaining CER should be concentrated on the 5 new classes — which
is a much easier, smaller problem to keep chipping away at. If it *doesn't*
move the needle, that's useful too: it would mean the drift hypothesis is
wrong and the shared-class errors really are irreducible CTC-alignment/
recognition issues from something else (e.g. this manuscript's hand being
a genuinely poor match for Sophro's original training material — the 3.3
scenario flagged in v3, not yet ruled out).

## 2. Corrected effort estimate for synthetic data (lever 2.1)

v3's report says "SogdianOCR v0.7 CycleGAN pipeline does not exist
publicly" and estimates a multi-day build. That's true for a CycleGAN
ink-aging bridge specifically, but it overstates the effort for basic
synthetic line generation: **kraken ships its own synthetic line generator**
— `ketos linegen` (CLI) / `kraken.linegen.LineGenerator` (Python API) —
which renders text through a Pango/Cairo pipeline using any installed font,
plus built-in degradation via `kraken.linegen.ocropy_degrade` and
`distort_line` (noise, slant, elastic distortion — the same noise model
`ocropus` used, tunable via the `-m/-s/-r/-d` linegen flags). This is
already in kraken's dependency tree (confirmed in your own 2.1 research
note) and requires no new pipeline to be built — it's a day of scripting
against an existing tool, not a multi-day CycleGAN build.

### Critical pre-check before generating anything (do this first — cheap, decisive)

The 3 Sogdian-specific codepoints (U+074D SOGDIAN ZHAIN, U+074E SOGDIAN
KHAPH, U+074F SOGDIAN FE) are recent, narrow Unicode additions to the
Syriac block. Standard Syriac fonts, including common choices like Noto
Sans Syriac, may not have glyphs for them at all — if they don't, `ketos
linegen` will render blank/tofu boxes exactly where you need the most help
(the rare classes), silently producing useless training images for the
classes that matter most.

Before generating any synthetic data: render one test line containing each
of the 3 codepoints with your candidate font and visually inspect the
output image. Do this for a couple of font candidates. **This is a
judgment call that likely needs your input rather than the agent's** —
picking a font that's not just glyph-complete but also a plausible visual
match for the c2av scribal hand (stroke width, ductus, degree of cursive
joining) is a paleographic assessment, not a technical one. Academic Syriac
font projects aimed at scholarly typesetting (rather than generic UI fonts)
are more likely to have complete coverage of specialist additions like the
Sogdian extensions — worth checking a couple of those alongside Noto
before committing.

### Once a font is confirmed

- Source text: pull running Sogdian text from the Sims-Williams lexicon
  corpus you already have (`dataset/lexicon/NSW2021corpus.xls`) or any
  other accessible Sogdian text — doesn't need to be c2av-specific content,
  just needs representative sequences, with the rare classes (rukkakha,
  zhain, fe) appearing much more densely than they do naturally, so bias
  the source text selection toward words containing them.
- Convert to Syriac script with your existing `scripts/latin_to_syriac.py`
  (or work in Syriac natively if the source is already in Syriac).
- Generate with `ketos linegen -f <font> -u NFC -m 0.15 -s 0.002 -r 0.001
  -d 2 <sogdian_text.txt>` (start with moderate degradation values close
  to kraken's tutorial defaults; tune once you see how the images look next
  to real c2av crops).
- Mix synthetic lines into the **training** split only — never into val or
  holdout — so evaluation numbers keep meaning what they've meant so far.
- Visual sanity-check a sample of generated lines against real c2av crops
  before training on them. This is also better done by you than the agent,
  for the same paleographic-plausibility reason as the font choice.

## 3. Cheap augmentation of the real 148 lines (do this before or alongside §2)

Rather than only generating wholly synthetic lines, apply kraken's own
`ocropy_degrade`/`distort_line` functions directly to the existing 148 real
line images to produce augmented duplicates — heavier noise/slant/elastic
distortion than whatever `--augment` currently applies by default. This
adds visual diversity without needing a font-coverage decision or new
source text, and directly targets the overfitting gap since the model
currently seems to be memorizing exact pixel patterns from only 148 unique
images. Much cheaper than §2 to try first; if it alone narrows the train/val
gap noticeably, that's a strong signal further data effort will pay off too.

## 4. Leave-one-plate-out cross-validation (no new data, more robust signal)

Right now generalization is estimated from one val plate (c2av11) and one
holdout plate (c2av12) — 34 lines total deciding the entire generalization
story for a model this overfit. With only 12 plates, rotate which plate is
held out across N training runs (as cheap as the existing recipe, ~1
GPU-hour each per the 0.2 timing) and look at the CER spread across folds,
not just one point estimate. Two things fall out of this for free:
- A much more trustworthy read on whether 71.43% is representative or got
  lucky/unlucky on this particular holdout plate.
- The option to **ensemble** the fold models (average logits or majority-
  vote decode) for final inference — ensembling independently-overfit
  models trained on different subsets is a standard, no-new-data way to
  claw back some accuracy when a single model overfits a small dataset.

## Suggested order

1. §1 classifier-row freeze — highest-confidence lever, directly explains
   an anomaly in your own 0.1 data, no new data required, one training run
   to test.
2. §3 heavier augmentation of real lines — cheap, no font/text-sourcing
   decisions needed, can run in parallel with #1.
3. §4 leave-one-plate-out CV — reuses the exact existing recipe, just more
   runs; do this once #1/#3 settle on a recipe, so the CV numbers reflect
   the best current setup.
4. §2 synthetic data via `ketos linegen` — highest ceiling, but gated on a
   font-coverage decision that's yours to make, not the agent's. Start the
   font-coverage check now (it's cheap) even while §1 and §3 are running,
   so it's not the long pole later.

## What needs you, not the agent

- **Font selection for §2**: glyph coverage + paleographic plausibility for
  the 3 Sogdian-specific codepoints is a scholarly judgment call.
- **Visual QA of synthetic lines** before they go into training — same
  reason.
- **Any further real annotation** of additional c2av (or other Turfan)
  plates — this is manual transcription work and is the only lever with no
  technical substitute; per v2/v3's own analysis it's still the only path
  to CER well below the current ceiling.
- **Deciding how much synthetic data to mix in** relative to the 148 real
  lines once §2 is running — a research-design call about how much to trust
  synthetic-vs-real balance, best made by you after seeing some real numbers
  back from a first small batch.

Everything else in this doc (the classifier-freeze fix, the augmentation
script, the CV/ensemble harness, the `ketos linegen` scripting itself) is
agent-executable without further input from you.
